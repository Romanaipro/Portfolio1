# Контракт форми та межа перевірки

Клієнт надсилає один POST на наявний HTTPS webhook n8n, без запасного `no-cors` запиту. Endpoint не змінено. Усі автоматичні перевірки підміняють мережу; бойові заявки не надсилалися.

Тіло — `application/x-www-form-urlencoded`: `name`, `contact`, `description`, `request_id` (UUID). Успіх дозволений лише за читабельної HTTP 2xx JSON-відповіді:

```json
{"accepted":true,"request_id":"той самий UUID"}
```

`accepted` має означати стійке збереження заявки або підтверджене прийняття в чергу. Це не підтверджує доставку в Telegram. Текст інтерфейсу повідомляє лише про прийняття сервером.

Наявний backend відсутній у репозиторії. Його фактичну відповідь та підтримку нового контракту **не перевірено**. До узгодження він може приймати дані, але клієнт чесно покаже невизначений результат. Альтернативні Telegram та email доступні завжди.

Невідомий/непрозорий/порожній JSON, мережна помилка або 8-секундний тайм-аут не очищують поля. Тайм-аут охоплює й читання тіла. Повтор вручну з незміненими полями в межах відкритої сторінки використовує той самий UUID. Зміна полів створює інший UUID. ID зберігається в пам’яті сторінки; після reload він не зберігається. Автоповторів немає. Клієнтський UUID сам по собі не запобігає дублюванню.

## Потрібно реалізувати й перевірити на staging приймача

1. Дозволити CORS для фактичного production origin; повертати читабельний JSON також для помилок.
2. Валідувати та нормалізувати поля; обмежити довжину, частоту запитів і розмір тіла на сервері.
3. Атомарно зберігати `request_id` як унікальний ключ разом із відбитком payload і станом обробки. Повтор того самого ID та payload повертає попереднє підтвердження; інший payload з тим самим ID — 409. Тривалість збереження ID має перевищувати погоджене вікно повтору.
4. Після фіксації заявки виконувати Telegram-сповіщення через стійку чергу/outbox; повтор доставки не повинен створювати другу заявку.
5. Перевірити втрату відповіді після commit, два одночасні POST з одним ID, повтор після timeout і збій між збереженням та Telegram. У базі має лишитися одна заявка; потрібні докази на рівні сервера.

Моки доводять поведінку клієнта. Серверна дедуплікація та доставка лишаються зовнішньою залежністю. Production endpoint не спрямовується на мок.
