# Схема вимірювання шляху

Збір не підключений. Перед активацією власник має обрати сервіс аналітики, правила приватності, термін зберігання та спосіб класифікації заявок.

| Подія | Коли | Дозволені параметри |
|---|---|---|
| `case_open` | Відкрито кейс, включно з прямим URL | `case_slug`, `source` = featured / filtered / service / deep_link |
| `contact_cta` | Перехід з кейсу, hero або пакета | `source`, `case_slug` або `plan_slug` |
| `form_start` | Перша зміна поля відвідувачем | `source`, `case_slug` або `plan_slug` |
| `form_result` | Завершення однієї спроби | `result` = accepted / error / unknown / timeout, `source` |

Не передавати ім’я, контакт, текст задачі, Telegram draft URL, повний URL з довільними параметрами або request_id. Технічний UUID призначений приймачу, а не аналітиці.

Воронку рахувати за унікальними сесіями в однаковому вікні: відвідувачі з відкритим кейсом → CTA → початок форми → **підтверджене** прийняття. Для кожного кроку знаменник — сесії попереднього кроку, додатково — усі сесії з кейсом. Повтори не рахувати як нові конверсії.

Релевантність заявки позначає власник у CRM за погодженими критеріями: задача входить до послуг, є спосіб зв’язку, зрозумілий потрібний процес. Текст та контакти лишаються в CRM. Частка релевантних — кількість позначених релевантними / усі прийняті заявки, для яких завершено оцінювання. Окремо рахувати неоцінені заявки.

Telegram/email є окремими виходами `direct_contact_click`, а не підтвердженими заявками. Lighthouse — лабораторія, не польові LCP/INP чи доказ зростання конверсії. Висновки про зручність потребують тестів із людьми.
